# CPU mitigation boot parameters: systemd-boot and kernel command lines

> [!abstract] The full chain
> **Kernel build supports the mechanism → edit the correct source → boot the intended artifact → inspect the effective command line → verify the resulting report.**
>
> Arch Linux x86_64 · reviewed **2026-10-29**. Related: [[CPU Vulnerabilities]] · [[CPU]] · [[CPU verification record]].

## 1. First identify which layer controls the argument

| Layer | Where arguments can come from | What editing it changes |
|---|---|---|
| Type #1 systemd-boot entry loading a separate kernel | `options` in the selected `.conf` entry | The bootloader-supplied command line for that entry |
| Generated Type #1 entry | Generator input such as `/etc/kernel/cmdline` | Future entries generated by that particular pipeline |
| Unified kernel image (UKI) | Embedded `.cmdline`, potentially supported addons/EFI inputs | Depends on the stub, signing policy, and selected artifact |
| Built-in kernel command line | `CONFIG_CMDLINE` and related build options | Requires changing/rebuilding the kernel to change the built-in source |

`/etc/kernel/cmdline` is **not a universal live configuration file**. systemd-boot does not read it at each boot to replace the `options` text in every existing entry. A generator must consume it and update the artifact you actually boot.

The [Boot Loader Specification](https://uapi-group.org/specifications/specs/boot_loader_specification/) defines Type #1 entries and Type #2 UKIs. Follow the selected artifact and update pipeline, not a remembered filename convention.

## 2. Inspect without writing boot files

```bash
uname -r
cat /proc/cmdline
sudo bootctl status --no-pager
sudo bootctl list --no-pager
boot_root=$(sudo bootctl --print-boot-path)
findmnt --target "$boot_root"
findmnt --target /
```

Use Bash for the multiline examples. `bootctl --print-boot-path` selects XBOOTLDR when present, otherwise the ESP. It avoids assuming that every installation uses `/boot`.

`findmnt --target` shows the filesystem containing a path. Confirm that the expected boot filesystem is mounted. On the current machine `/boot` is a separate vfat mount. The old `findmnt / /boot` example was not a reliable way to query two targets; use separate invocations.

From `bootctl list`, record:

- The selected entry ID and its **source** path.
- Whether it loads a separate kernel/initramfs or a UKI.
- The actual kernel and initrd paths.
- Its current options.

`bootctl list` describes on-disk entries now. `/proc/cmdline` describes the running boot. An entry can have been edited since boot; a built-in prefix can also make these strings differ.

### Current local layout, for orientation only

The verified machine uses systemd-boot 262.1-1-arch with these Type #1 entries on `/boot`:

| Entry ID | Observed role |
|---|---|
| `linux-dusky-battery.conf` | Selected/default; separate battery kernel and initramfs |
| `arch-linux.conf` | Installed stock Linux kernel entry |
| `arch-linux-fallback.conf` | Same stock kernel with a fallback initramfs |

These are not the machine-ID/version-named entries described in the old notes. There is no current `/etc/kernel/cmdline` file. `kernel-install inspect` describes a **possible generated BLS pipeline**, but that does not prove this is the pipeline that produced the selected static entry.

A fallback initramfs provides a different boot image, not a different kernel build or a frozen known-good kernel. Updating shared kernel/image files can affect several entries at once.

## 3. Check compile-time support before experimenting

```bash
zcat /proc/config.gz | grep -E 'CONFIG_CPU_MITIGATIONS|CONFIG_MITIGATION_|CONFIG_CMDLINE'
```

The running battery kernel has:

```text
# CONFIG_CPU_MITIGATIONS is not set
CONFIG_CMDLINE_BOOL=y
# CONFIG_CMDLINE_OVERRIDE is not set
```

Its `CONFIG_CMDLINE` includes `mitigations=off` and other defaults. The runtime log explicitly says it ignores `mitigations` because the kernel was compiled without mitigations.

Consequences:

1. Removing that option from a Type #1 entry does not remove the compiled-in copy.
2. Supplying `mitigations=auto` cannot enable mitigation code omitted from this build.
3. A proper enabled/disabled comparison must use a kernel containing the relevant code.
4. Do not assume a duplicate boot argument always follows a universal “last one wins” rule. Parsing depends on the specific parameter and build behavior.

`/proc/config.gz` is for the running kernel only. If experimenting with another installed kernel, inspect its matching configuration or boot it and inspect there. The stock entry exists, but its runtime mitigation behavior was not tested in this review.

For argument definitions, see [[CPU Vulnerabilities]] and the [kernel parameter reference](https://docs.kernel.org/admin-guide/kernel-parameters.html). All write/reboot procedures below are documented workflows, **not actions performed during this review**.

## 4. One boot only: the boot menu editor

For a normal systemd-boot Type #1 entry, the boot-menu editor can modify the command line for that boot:

1. Enter the systemd-boot menu; holding **Space** during startup can expose it.
2. Select the intended entry and press **e**.
3. Edit the command line while preserving required root/storage arguments.
4. Boot it and inspect the runtime results below.

This depends on the loader's editor setting and the selected image/policy allowing external options. Check `man systemd-boot` and `man loader.conf` on the actual system. UKIs, Secure Boot restrictions, and built-in kernel arguments can alter the effective result.

This method does not persist an experiment in a configuration file. It was documentation-checked, not tested by rebooting the workstation.

## 5. A separate Type #1 test entry

This is useful for repeated experiments while keeping the original entry's text available.

### Choose and back up the actual entry

Run the discovery commands in section 2 first. Set `entry_id` from the **real** `bootctl list` output; the following name exists locally:

```bash
entry_id=arch-linux.conf
src="$boot_root/loader/entries/$entry_id"
backup_dir="$HOME/.local/state/cpu-boot-tests/$(date +%Y%m%d-%H%M%S)"
mkdir -p -- "$backup_dir"
sudo cat -- "$src" > "$backup_dir/$entry_id"
```

This makes a persistent text backup in your own state directory without needing permission to read `/boot` as an ordinary user. Record which backup belongs to which experiment.

### Copy and edit

Choose a new, unused test-entry filename:

```bash
dst="$boot_root/loader/entries/cpu-mitigation-test.conf"
sudo cp -- "$src" "$dst"
sudoedit "$dst"
```

Change the `title` to identify the experiment. For a **new** parameter, append it to the existing `options` line. If that parameter already exists, edit the existing value rather than accumulating duplicate alternatives. Preserve all unrelated arguments and every required boot/storage field.

For example, a deliberate global-disable experiment adds:

```text
mitigations=off
```

An enabled comparison may need `mitigations=auto` and removal of conflicting vulnerability-specific overrides, on a kernel built with the required support. See [[CPU Vulnerabilities]]. Do not treat this as a suggested everyday configuration.

### Preserve these relationships

The actual entry can require `root=`, `rootflags=`, encryption or volume-management options, `resume=`, and other initramfs-specific arguments. Preserve the existing bootable values, not values copied from someone else's machine. A root filesystem is not necessarily Btrfs, unencrypted, or at subvolume `@`.

Schematic entry structure only:

```ini
title   Arch Linux CPU experiment
linux   /path-relative-to-boot-partition/kernel
initrd  /path-relative-to-boot-partition/initramfs
options EXISTING_WORKING_ARGUMENTS EXPERIMENT_PARAMETER
```

The placeholders above are not a bootable configuration. Copy the selected working entry rather than retyping this skeleton. Multiple `initrd` lines may be meaningful, including a separate microcode image; retain their ordering.

### Inspect before booting

```bash
sudo diff -u -- "$src" "$dst"
sudo bootctl list --no-pager
```

A `diff` exit status of 1 means the files differ, which is expected. Inspect the changed title and parameter. For a text-only edit of an existing Type #1 separate-kernel entry, rebuilding the initramfs or reinstalling systemd-boot is not normally needed.

Choose the test entry manually, or optionally set it for the next boot:

```bash
sudo bootctl set-oneshot cpu-mitigation-test.conf
```

This writes an EFI boot selection; it does not reboot immediately and does not permanently change the default. It was checked against installed documentation, not executed in this review. Reboot when ready through the normal desktop/system workflow.

## 6. Persistence depends on the generator

### Static Type #1 entries

If an entry's text is maintained directly, its `options` line is the relevant source. A package hook, installer, local script, or boot-management tool can overwrite it later. Inspect the actual update mechanism before claiming persistence.

Relevant read-only investigation:

```bash
sudo kernel-install inspect
kernel-install list
ls /etc/mkinitcpio.d/
grep '^HOOKS=' /etc/mkinitcpio.conf
```

Then inspect the particular preset, hook, or generator that owns the selected files. Do not infer “all entries are generated by kernel-install” just because the command exists.

On this machine, inspected ALPM hooks invoke `/usr/share/libalpm/scripts/mkinitcpio`, and presets name flat `/boot/vmlinuz-*` and `/boot/initramfs-*.img` paths. The selected entry references those paths. The inspected hook does not establish that `90-loaderentry.install` regenerates that selected entry.

### kernel-install BLS entries

For an installation **actually managed by this pipeline**, the installed systemd 262.1 `90-loaderentry.install` normally obtains options from the first applicable source:

1. `/etc/kernel/cmdline`.
2. `/usr/lib/kernel/cmdline`.
3. `/proc/cmdline`, with `BOOT_IMAGE=` and `initrd=` tokens removed, outside a container.

An explicit `KERNEL_INSTALL_CONF_ROOT` changes this selection to its configured root; inspect it when using a custom invocation. The script may append `systemd.machine_id=` when entry-token policy requires it.

Use one line of the **reviewed intended command line** in `/etc/kernel/cmdline`:

```bash
sudoedit /etc/kernel/cmdline
```

Do not blindly seed it from `/proc/cmdline`: the current boot may contain one-time experiments or a compiled-in prefix. On the verified kernel, copying `/proc/cmdline` verbatim would duplicate built-in defaults and carry an `initrd=` token into a persistent file.

Before regenerating:

```bash
kernel_version=$(uname -r)
kernel_image="/usr/lib/modules/$kernel_version/vmlinuz"
sudo kernel-install inspect "$kernel_version" "$kernel_image"
```

`uname -r` selects the **running** kernel, not the newest installed one. Choose an installed version deliberately when that is the intended target. `inspect` reveals the proposed layout, plugins, boot root, and entry name; it does not regenerate them.

Only after confirming this is the desired pipeline:

```bash
sudo kernel-install add "$kernel_version" "$kernel_image"
```

This is a real mutation: installed plugins may rebuild an initramfs and install a kernel/entry. On the current layout it would create a token/version-named entry, not simply edit `linux-dusky-battery.conf`. Do not run it as a generic “refresh boot flags” command.

The installed generator was exercised in a temporary fixture with a supplied command-line source, dummy kernel, and dummy initrd. It produced the expected options and relative image paths. The real `kernel-install add` workflow was not executed. See the [systemd kernel-install reference](https://www.freedesktop.org/software/systemd/man/latest/kernel-install.html).

## 7. UKIs: change the image that will actually boot

A UKI may embed the kernel, initramfs, and a `.cmdline` section. Rebuilding an unrelated Type #1 text entry does not rewrite that embedded command line.

Inspect:

1. Which `.efi` file the selected entry loads.
2. Which installed generator/preset builds it.
3. Where that generator obtains the command line.
4. Whether signing and installed-key policy apply.
5. Which final image was installed on the boot filesystem.

With systemd-stub, Secure Boot plus an embedded `.cmdline` normally prevents ordinary external load options from replacing that command line. Other supported inputs/addons exist; consult the installed `systemd-stub(7)` documentation rather than claiming that every UKI ignores every external option in every configuration.

Change the actual generator input, rebuild through that pipeline, and sign through the existing signing workflow if required. Do not assume `ukify`, `sbctl`, or a particular mkinitcpio preset is installed. This workstation's selected entry is a separate-kernel Type #1 entry, so no UKI rebuild/signing was tested.

## 8. Verify after reboot

```bash
uname -r
sudo bootctl status --no-pager
cat /proc/cmdline
zcat /proc/config.gz | grep -E 'CONFIG_CPU_MITIGATIONS|CONFIG_MITIGATION_|CONFIG_CMDLINE'
grep -H . /sys/devices/system/cpu/vulnerabilities/*
journalctl -k -b --no-pager --grep='microcode|mitigat|Unknown kernel command|compiled without'
```

These answer separate questions:

| Evidence | What it establishes |
|---|---|
| `uname -r` | Running kernel release |
| Current entry in `bootctl status` | Loader-reported selected entry |
| `/proc/cmdline` | Effective supplied argument string, including built-in input |
| Running config | Compiled support and command-line build options |
| Sysfs reports | Kernel's assessed vulnerability/mitigation state |
| Boot journal | Early decisions, ignored/unknown options, microcode loading |

A parameter can be present yet ignored. A missing “unknown parameter” warning is not proof that a setting took effect. Some unrecognized kernel arguments are passed onward to userspace; initramfs arguments can also legitimately appear on the kernel command line.

Record the observations with benchmark results. Do not call a reboot-dependent change verified until you have booted it and inspected the result.

## 9. Troubleshooting

| Observation | Check next |
|---|---|
| Desired option missing from `/proc/cmdline` | Selected entry, artifact path, generator input, and whether the artifact was rebuilt |
| `/proc/cmdline` has options absent from the entry | Built-in `CONFIG_CMDLINE`, UKI/stub inputs, or boot-time edits |
| Desired option appears but status is unchanged | Compiled support, hardware applicability, microcode, parameter spelling, and interacting mitigations |
| Log says “compiled without mitigations” | Boot a suitable build; an argument cannot add omitted code |
| Entry reverts after a package update | Find and update its actual generator source |
| Editing `/etc/kernel/cmdline` does nothing | Existing static entry or different pipeline; inspect which source is consumed |
| Kernel update changed several entries' behavior | They may share the updated kernel/initramfs paths |
| A copied entry was expected to be a kernel rollback | Copying entry text does not preserve older kernel/image files |
| Mount path exists but edits have no boot effect | Confirm the intended ESP/XBOOTLDR is mounted and selected |

## 10. Rollback

If only the separate experiment entry changed:

1. Boot the original entry.
2. Verify the running kernel, command line, and reports.
3. Remove the test entry when it is no longer useful, after identifying its exact path.

If you edited an existing entry, restore its saved text or remove the specific experiment parameter. If you changed a generator's input, restore that input and regenerate the corresponding artifacts. If a UKI changed, restore/rebuild the actual UKI through its signing/install pipeline.

On this machine `/boot` is a separate vfat filesystem. A Btrfs snapshot of `/` does not include it. More generally, verify snapshot boundaries and keep boot assets needed for an actual kernel rollback; a text-entry backup alone is not that rollback.

## 11. Limine on a different installation

Limine is not the selected bootloader here and no local Limine boot was tested. The old note's `:Entry` and `KEY=value` configuration example was obsolete for the reviewed upstream format.

Current [Limine configuration documentation](https://github.com/limine-bootloader/limine/blob/trunk/CONFIG.md) uses `/Entry title` and `key: value`. A schematic Linux-protocol entry is:

```text
/Arch Linux CPU experiment
    protocol: linux
    path: boot():/vmlinuz-linux
    module_path: boot():/initramfs-linux.img
    cmdline: EXISTING_WORKING_ROOT_AND_STORAGE_ARGUMENTS mitigations=off
```

This is not a complete bootable example: retain that installation's discovered paths and existing working arguments. Edit the configuration file actually used by its installed Limine version, or the generator input if it is generated. Editing a command-line value alone does not require reinstalling the bootloader binary. Kernel build support and post-boot verification remain necessary.
